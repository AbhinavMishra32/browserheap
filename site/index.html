A browser for agents.
Idle tabs sleep. Nothing breaks.

        
Agents open tab after tab and never close them. Browserheap keeps the 2 tabs your agent is using live and puts the rest to sleep. The pages your agent holds keep working, and a sleeping tab wakes the moment it's touched.

The problem

        01
        
Agents open tabs. They don't close them.

        
A research task opens a search, five results, two docs pages and a forum thread. The agent reads each one and moves on. Every tab stays open, holding a full page in memory, and nothing ever goes back to it.

      

      

        

          vercel-labs/agent-browser #885
          
60+ tabs and the CPU pinned

          
Users report 60 or more tabs piling up across agent sessions, with the browser pinned above 100% CPU.

          
The fix proposed: an idle timeout that closes the whole browser.

          Read the issue
        

        

          browser-use/browser-use #5484
          
Tabs that pile up for days

          
Long-running agents collect tabs for days until the machine slows down.

          
The fixes suggested: close old tabs, or restart Chrome.

          Read the issue
        

        

          browserheap
          
Sleep them instead

          
Closing tabs loses the agent's work. Restarting Chrome loses its logins. Browserheap puts idle tabs to sleep and brings them back when the agent needs them.

          
Nothing is lost: same URL, same scroll position, still signed in.

        

      

    

  


  

    

      

        
How it works

        02
        
Two tabs live. The rest asleep, and still there.

        
The agent never manages any of this. It opens tabs and uses them; Browserheap decides which ones get to hold memory.

      

      

        

          

          state 1 · live
          
The 2 tabs in use

          
The tabs the agent used most recently are real Chromium pages. Raise the count with --live.

        

        

          

          state 2 · asleep
          
Kept, not running

          
A sleeping tab is closed and kept as its URL, title, scroll position and text. The agent can still read it without waking it. Tabs with unsent typing never sleep.

        

        

          

          state 3 · waking
          
Back when touched

          
Click, type or read the live page and the tab comes back where it was, with the same cookies.

          274ms to wake
        

      

    

  


  

    

      

        
Handles that survive sleep

        03
        
Pages belong to the tab. Not to Chromium.

        
Other agent browsers hand the agent a raw page. Close it and every reference the agent holds goes stale. Browserheap hands out pages and locators that follow their tab, so sleeping and waking happen underneath without the agent's code noticing.

        
    
          
  • A page kept in a variable still works after its tab sleeps.
    • 
          
  • Locators by role, text, label or CSS keep working too.
    • 
          
  • Reading a sleeping tab's title or text doesn't wake it.
    • 
        

      

      

        
agent's code · repl


const docs = await openTab("react.dev")
await openTab("news.ycombinator.com")
await openTab("github.com/trending")
// 3 tabs, 2 live: docs is asleep now

docs.isAsleep()            // true
await docs.title()         // "React", without waking it

await docs.getByRole("link", { name: "Learn" }).click()
// docs wakes in ~0.3 s and the click lands

Use it

        06
        
Give it to your agent. Three ways.

      

      

        

          
          
          
        

        

          

            
Drop in the skill

            
Add the skill file to your agent and it learns the loop: open a page, read its snapshot, act with Playwright-style JavaScript, look at what changed.

            
The skill ships in the package under skills/browserheap/SKILL.md.

          

          

            
terminal


# once
$ npm install -g browserheap
$ browserheap install        # downloads Chromium
$ cp -r "$(npm root -g)/browserheap/skills/browserheap" ~/.claude/skills/

# then ask your agent
"Compare the pricing pages of Vercel, Netlify and Render"

          

        

        

          

            
Drive it from any shell

            
A background browser starts on first use and stops after 30 idle minutes. Variables live between run calls, so an agent can work step by step.

            
Use --session for a separate browser per task, --live 4 to keep more tabs awake.

          

          

            
terminal


$ npx browserheap open https://news.ycombinator.com
# prints the page as a tree: link "new" [ref=e14]

$ npx browserheap run 'await page.locator("e14").click()
  console.log((await snapshot(page)).diff)'

$ npx browserheap tabs        # live or asleep, title, url
$ npx browserheap stop

          

        

        

          

            
Build it into your agent

            
startSession() gives you the browser and its REPL: wrap session.run as one tool in pi, the AI SDK, LangChain or your own loop.

            
Have your own tools already? launch() gives you just the sleeping tabs, with real Playwright pages underneath.

          

          

            
agent.ts


import { startSession } from "browserheap"

const session = await startSession({ maxLive: 2 })

// your agent's browser tool
async function browser(code) {
  return session.run(code)   // text and images back
}

await session.close()

          

        

      

    

  


  

    

      

        
Limits

        
What sleeping costs.

      

      

        
refs
Snapshot refs don't survive a wake
Refs like e12 belong to the page as it was. After a tab wakes, take a new snapshot. An old ref fails with a message saying so.

        
page state
What only the running page knew is gone
An open menu, a half-played video or unsaved page state go when a tab sleeps. URL, scroll, cookies and logins come back.

        
live tabs
Live tabs cost what Chrome costs
A live tab is a real Chromium page. Keep more live with --live when an agent works across several at once.

        
mcp
An MCP server is next
Today it's a CLI, a skill file and an SDK. An MCP server for apps that only speak MCP is on the way.
